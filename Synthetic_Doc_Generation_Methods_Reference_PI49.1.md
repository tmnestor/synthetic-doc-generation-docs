# Synthetic Document Generation: Methods & Packages Reference

**Work item:** #5147049 — *Synthetic document image dataset: Research Gen AI / non Gen AI methods for generating synthetic documents* (Area `EST\SDP\MDT\GEN AI`, `PI49\Sprint 49.1`).

**Acceptance criterion addressed:** a reference of extant methods/packages for synthetic document generation, with an evaluation of their advantages and disadvantages, to inform feature decisions for the in-house `Synthetic_Doc_Generation` pipeline.

**Purpose of the pipeline (for context):** a labelled Australian business-document benchmark used to measure the **information-extraction (IE) accuracy of competing Vision-Language Models** — i.e. the synthetic ground truth is the answer key, not model training data.

**Method:** multi-source web survey with adversarial claim verification (6 search angles, 17 primary sources fetched, 79 candidate claims, 25 verified by 3-vote panels; 24 confirmed, 1 refuted). Verification votes and confidence are recorded inline and in the appendix. Date: 2026-07-24.

---

## 1. Executive summary (bottom line up front)

1. **External credibility for a synthetic IE benchmark comes from the evaluation standards and formats it stands on, not from the generator.** The pipeline already exports to **DocILE** and **CORD** and scores with their permissively-licensed reference scorers — this is the defensible core.
2. **The field's own flagship benchmark legitimises a bespoke generator.** DocILE — the most-cited business-document IE benchmark — was itself produced by a *bespoke, proprietary, rule-based HTML-to-PDF synthesiser* seeded by 100 real layouts and filled with a fake-data library, then validated empirically `[arXiv:2302.05658]`. The accepted, peer-reviewed construction is exactly "bespoke generator → recognised formats → recognised scorers". The field does **not** expect adoption of a named OSS generator.
3. **No recognised OSS generator emits field-level KILE/LIR bounding boxes.** The capability the benchmark needs (render-time, per-field boxes) is genuinely bespoke-only today; every recognised OSS generator either targets a different task, is copyleft, or is an unreleased preprint.
4. **The permissive OSS worth adopting is narrow:** Augraphy (degradation), and optionally SynthDoG/SynthTIGER as recognised text-render components. These reduce bespoke surface without compromising the answer key.
5. **The synthetic-to-real gap is real and must be acknowledged**, not assumed away — the ticket's premise that "Gen AI has advanced synthetic generation" holds for *training augmentation* but not for *answer-key fidelity*. Triangulate against a small real/held-out set.

---

## 2. The credibility question, answered directly

> *Is a bespoke generator defensible when it exports to recognised formats and is scored with recognised scorers, or does the field expect a named OSS generator?*

**A bespoke generator is defensible — with direct peer-reviewed precedent.** DocILE's 100,000-document synthetic subset (the first large synthetic dataset carrying KILE+LIR labels) was generated by a proprietary rule-based synthesiser that fills annotated fields via content generators (some using the **Mimesis** fake-data library — the same *class* of tool as this pipeline's incumbent Faker), renders HTML to PDF, and uses layouts inspired by 100 fully-annotated real documents (one per layout cluster). Synthetic pre-training then improved KILE and LIR in all cases but one, and the best benchmark-permitted result used the synthetic data `[arXiv:2302.05658]` *(construction facts verified 3-0; empirical-validation claim verified 2-1 — see appendix)*.

**Implication for the credibility narrative:** the pipeline should be positioned as *"a bespoke domain generator that exports to the recognised DocILE (KILE/LIR) and CORD formats and is scored with their published MIT reference scorers"* — the identical pattern the field's flagship benchmark used. This is a stronger defence than adopting an OSS generator would have been, because the OSS generators do not produce the required labels (§3).

## 3. Generation methods & packages — advantages / disadvantages

**Legend:** *Field-level bbox GT* = does the tool emit per-field (KILE/LIR-style) bounding-box ground truth out of the box? This is the benchmark's hard requirement.

### 3.1 Comparison table

| Method / package | Licence | Field-level bbox GT | Air-gap (pure pip/conda) | Advantages | Disadvantages | Fit |
|---|---|---|---|---|---|---|
| **SynthDoG** (NAVER, in Donut) `[clovaai/donut]` | **MIT** ✅ | ❌ text-sequence only (`{"text_sequence": "…"}`) | ✅ | Recognised, widely-cited; cheap multilingual text rendering | No field boxes; content is not schema-structured | **Adopt as text-render component only** |
| **SynthTIGER** (NAVER) `[arXiv:2107.09313; clovaai/synthtiger]` | **MIT** ✅ | ❌ glyph/word-crop boxes (in `coords.txt`), not document fields | ✅ | Recognised scene-text-recognition generator; reproducible | Produces single-word/line crops, not document layouts | Niche; not a document GT source |
| **Augraphy** `[arXiv:2208.14558]` | **MIT** ✅ | ❌ — but **transforms user-supplied boxes** to stay aligned with degraded output | ✅ | Realistic print/scan/fax/ink degradation; recognised; box-preserving | Does not generate content or boxes | **Adopt as post-hoc degradation layer** |
| **DocSynth** (ICDAR'21) `[arXiv:2107.02638]` | research code | ❌ layout is an *input*, images are the output | — | Realistic layout-conditioned image synthesis | Targets layout-analysis augmentation, not key-value IE | Wrong task |
| **LayoutDM** `[arXiv:2303.08137]` | research code | ❌ element-box geometry only; no rendered text | — | Strong controllable layout geometry | No text, no extraction labels | Wrong task |
| **SynthDoc** `[arXiv:2408.14764]` | research code | ❌ image-text pairs (Donut-style) | — | Handles text+tables+charts for VDU | Reading-oriented, 5k-pair benchmark; no field boxes | Wrong task |
| **DocSynth-300K** / DocLayout-YOLO `[arXiv:2410.12628]` | ⚠️ **AGPL-3.0** (verified in `pyproject.toml`) | ❌ region-category labels (YOLO), not key-value | — | Large-scale layout data via Mesh-candidate BestFit | **Strong copyleft — fails the permissive-licence constraint**; wrong task | **Excluded on licence** |
| **SAYRE** (Alibaba/Qwen, Jul 2026) `[arXiv:2607.04636]` | unreleased/unlicensed preprint | ✅ produces document-schema-annotation triples | ❌ not confirmed | Generates KIE data at scale from few exemplars, no templates | Preprint; no confirmed released, permissive, air-gap build | **Cite as SOTA precedent only** |
| **DocDjinn** (Lamott et al., Feb 2026) `[arXiv:2602.21824]` | unreleased/unlicensed preprint | ✅ annotated documents from unlabeled seeds | ❌ not confirmed | VLM-based; clustering seed selection; parametrised sampling | Single-team preprint; availability/licence unknown | **Cite as SOTA precedent only** |
| **Bespoke Pillow generator** (incumbent) | in-house (permissive deps) | ✅ **render-time, per-field** | ✅ | Exact AU + trust-distribution fidelity; byte-stable; DocILE/CORD export | Maintenance burden; in-house provenance | **Retain — nothing recognised replaces it** |

### 3.2 Reading of the table

- **Gen-AI methods** (LayoutDM, DocSynth, SAYRE, DocDjinn) are either geometry/layout-only, target the wrong task, or are unreleased preprints. The two that *do* emit KIE labels (SAYRE, DocDjinn) are not adoptable components today. The ticket's premise that Gen AI has advanced synthetic *document* generation is true for realism and for training-data augmentation, but the answer-key-grade field labelling a benchmark needs is not yet available as permissive OSS.
- **Non-Gen-AI methods** (SynthDoG/SynthTIGER text rendering, Augraphy degradation, template/programmatic rendering as used in the incumbent) are the permissive, air-gap-friendly, recognised building blocks — but none supplies field-level boxes except a bespoke renderer instrumented to emit them at draw time.
- **The one hard exclusion on licence grounds:** DocLayout-YOLO / DocSynth-300K generation code is **AGPL-3.0**, unsuitable for this environment regardless of task fit.

## 4. Recognised datasets, formats & scorers (the credibility backbone)

### 4.1 Formats & scorers — adopt these

| Standard | What it defines | Ground truth | Metric | Reference scorer licence |
|---|---|---|---|---|
| **DocILE** `[arXiv:2302.05658; rossumai/docile]` | Two field-level IE tasks: **KILE** (Key Information Localisation & Extraction) and **LIR** (Line Item Recognition), for invoices/orders | Per field: `(bounding box + page, field type, text)`; LIR fields also carry a line-item ID | **AP** for KILE (CLEval pseudo-character-centre, not IoU); **micro-F1** for LIR | **MIT** (scorer + loader, verified against raw `LICENSE`) — **air-gap vendorable** ✅ |
| **CORD** `[clovaai/cord]` | Receipt IE with hierarchical `gt_parse` | Field-level bounding boxes + OCR text + hierarchical parse | Tree-edit-distance accuracy over `gt_parse` | Public release; already exported to by the pipeline |

**Critical licence scoping — state this explicitly in any write-up:** DocILE's **MIT covers the code/scorer only**. The DocILE **dataset** requires a Dataset Access Request under separate research terms. The pipeline's approach (vendor the MIT scorer; export *in-house* AU data to the DocILE format) relies solely on the MIT code, so the constraint is satisfied — but do not conflate "we use the DocILE format/scorer" with "we redistribute the DocILE dataset". `[rossumai/docile LICENSE — verified 3-0]`

### 4.2 Datasets for triangulation — *partially verified in this pass*

DocILE (invoices/orders, field-level boxes) and CORD (receipts, field-level boxes, `gt_parse`) were verified. The remaining named datasets (**SROIE, FUNSD, RVL-CDIP, DocVQA, DUDE**) were part of the brief but **did not surface as separately verified claims** in this run — their per-dataset licence and bounding-box availability are **UNVERIFIED here** and are listed as an open question (§6). Do not assert their terms without a follow-up pass.

## 5. The synthetic-to-real gap — honest caveats

- **Best-case published augmentation reaches ~87% of full-real performance** (DocDjinn, 100 real + 140k synthetic, averaged over eleven benchmarks) — but this is a single-team, unreviewed preprint self-report, an average masking per-task variance `[arXiv:2602.21824 — verified 2-1]`.
- **Synthetic pre-training helps but is not uniformly monotonic** — DocILE's own results improved in all cases except LIR for one RoBERTa configuration `[arXiv:2302.05658 — verified 2-1]`.
- **Consequence for this benchmark:** report VLM extraction scores against the synthetic set **alongside a small real/held-out validation set**, so results are triangulated rather than synthetic-only. This is both good practice and a pre-emptive answer to the obvious external critique of a synthetic benchmark.

## 6. Recommendation — hybrid, mapped to requirements

**Adopt (recognised, permissive, air-gap-safe) — for credibility:**
- **DocILE KILE/LIR format + MIT scorer** — already in place; keep and foreground it.
- **CORD `gt_parse` export** — already in place.
- **Augraphy (MIT)** — recognised degradation layer stacked *after* box generation; preserves supplied boxes.
- *Optional:* **SynthDoG/SynthTIGER (MIT)** as recognised text-render components where useful.

**Retain as bespoke — defensible because no permissive OSS covers it, citing DocILE's own construction as precedent:**
- Australian + trust-distribution content fidelity (checksum-valid ABN/TFN, GST = total/11, transaction/quad linking).
- **Render-time, field-level bounding boxes** (the KILE/LIR requirement no OSS generator emits).
- Byte-stable reproducibility (pinned Pillow font metrics).
- Air-gapped operation with no runtime external calls.

**Do not adopt:**
- DocLayout-YOLO / DocSynth-300K generator (**AGPL-3.0**).
- SAYRE / DocDjinn as components (unreleased preprints) — cite as method precedent only, and re-check their repos before relying on them.

**One-line positioning statement for leadership:** *"Our benchmark stands on the field's recognised evaluation standards — DocILE (KILE/LIR) and CORD, with their published MIT scorers — exactly as the flagship DocILE benchmark itself was constructed; the only bespoke element is the Australian/trust domain generator with render-time field boxes, a capability no permissively-licensed open-source tool provides."*
